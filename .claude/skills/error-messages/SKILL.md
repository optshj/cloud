# 에러 메시지

`docs/CONVENTIONS.md` 원칙("실패했습니다" 금지 — 원인이 드러나야 한다)을 이 프로젝트의 실제 코드 형태로 구체화한 것. **두 층을 분리해서 생각한다.**

- **사용자 문구**(`NextResponse.json({ error: ... })`, toast) — 짧고 친근한 톤 유지. `"로그인이 필요해요"` 같은 기존 문구들은 그대로 좋다. 이 층을 장황하게 만들 필요 없음.
- **원인 정보**(서버 로그, 혹은 최소한 클라이언트 콘솔) — 나중에 사람이든 에이전트든 이 로그만 보고 원인을 추적할 수 있어야 한다. 이 층이 비어있는 게 문제.

## 체크

- **catch에서 원본 에러를 그냥 버리고 고정 문구만 반환** — 🔴. `catch (error) { return NextResponse.json({ error: "저장에 실패했어요" }) }`처럼 `error` 객체를 한 번도 안 쓰면, 나중에 이 500이 재현됐을 때 로그에 아무 단서가 없다. 사용자 문구는 그대로 두되 앞에 `console.error("<route>: <동작 설명>", error)`를 추가한다.
- **알려진 에러를 구분 없이 뭉뚱그림** — Postgres unique violation(`error.code === "23505"`) 같은 특정 에러 코드로 원인을 분기할 수 있는데도 그냥 catch 하나로 합쳐 처리하면, 각각 다른 문구/상태 코드를 줄 수 있는데도 놓치는 것이다. 구분 안 하면 🟡.
- **클라이언트가 서버 에러를 화면에 그대로 흘려보내기만 하고 콘솔에 안 남김** — `err instanceof Error ? err.message : "..."`처럼 서버 응답 문구를 UI에만 보여주고 `console.error`가 없으면, 서버가 로그를 안 남기는 경로(네트워크 에러, 응답 파싱 실패 등)에서 원인이 완전히 사라진다. UI 문구와 별개로 `console.error(err)`는 남긴다.
- **여러 실패 지점이 차별점 없는 문구로 작성됨** — 인증 실패/입력 검증 실패/외부 API 실패가 전부 "잘못된 요청이에요"면 어디서 막혔는지 구분이 안 된다. 최소한 status code나 로그 메시지로는 구분한다.

## 하지 않는 것

- 사용자 문구를 기술적으로(스택트레이스, 에러 코드 노출 등) 바꾸지 않는다 — 제품 톤(캐주얼한 반말체 아닌 해요체)은 유지. 원인 정보는 로그 쪽에 쌓는다.
